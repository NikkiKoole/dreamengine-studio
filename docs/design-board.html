MIDI OUT CANNOT REACH THE HOST, and this rack is already the sequencer (OPEN, 2026-08-15). Found while surveying the AUv3 component types: everything in the MIDI OUT block is FINISHED work (303a ch1 / 303b ch2 / 808 GM ch10 / 909 GM ch11, slides as overlapping notes, accents as velocity, real drum gate lengths, 24ppqn clock, start/stop, a shutdown flush that never strands a held note) and it all goes to a CoreMIDI VIRTUAL SOURCE, which is the STANDALONE path. A plug-in's MIDI reaches its host through the AU's MIDIOutputEventBlock, and the engine has NO outward seam at all: ios/Sources/engine.h exports audio-in, notes, bend, CC and transport, and nothing the other way; the AU declares neither MIDIOutputEventBlock nor midiOutputNames (grepped, zero hits). So under a DAW the pattern leaves by a side door the project cannot record, route or save. THE CART SIDE IS DONE (mout_on already gates it, the pattern already streams) and the work is engine + Swift: a ring behind midi_send_* plus something like de_midi_out_drain(DeInstance*, DeMidiOut*, int) for the render block to pull. midi_output.h already tracks held notes per channel for its shutdown flush, so most of the bookkeeping exists. WHY IT MATTERS BEYOND A BUGFIX: with it this rack is also an `aumi` MIDI PROCESSOR that plays the user's OTHER plug-ins, which is near-zero CPU in the host (the constraint that kills every richer idea), competes on a much emptier shelf than the synth slot, and makes the PANEL the entire product. Open question in the design: does the ring REPLACE the virtual source in a plug-in build or run alongside it (an appex publishing a system-wide port is flagged uncovered). HOST PARAMETERS (a DAW can automate + record the knobs): SHIPPED (2026-08-15), except host READ-BACK. Came out of the maker asking 'is any of this recordable or usable in a way? not really I guess' - and the answer was mostly YES (the host records the MIDI notes, which is arrangement, the thing this rack never had) with one big NO: the AUv3 exposed NO AUParameterTree AT ALL, so a host saw ZERO parameters. Nothing automatable, nothing recordable, an empty lane menu. That also reframes the mod wheel work of the day before: mapping CC1 to the master filter was a WORKAROUND for having no parameters, not a design anyone would choose. THE MODEL - the parameter IS the knob: param_bind(addr, &knob, name, lo, hi) takes a pointer to a float the cart ALREADY OWNS, so the panel keeps dragging it, the DSP keeps reading it, and the host now reads and writes that same float. One storage location, not two, which is why 'the host automates it' / 'the panel follows automation' / 'a drag shows up in the host lane' are the SAME FACT rather than three sync paths to keep honest. The cart changed nothing else - 21 param_bind calls and no edit to any drawing or DSP code. The TREE IS BUILT FROM WHAT THE CART DECLARED, never a table in Swift: that would be a second source of truth for a fantasy console whose whole point is swapping carts. WHAT IS EXPOSED and why not everything: 21 - the MST performance set (FLT/RES/GLU/FB/PUMP), the acid five on each 303, DIST/SEND/VERB on each drum machine. The rack has ~40 knob sites; the per-voice drum tone knobs, the p-lock lanes and the pattern editors are deliberately OUT - they are how you BUILD the sound, the session blob already carries them, and every parameter lives in the host's menu forever. ADDRESSES ARE FOREVER: a saved project's automation stores nothing but the number, so changing what one means silently re-points somebody's lane at a different knob, with no version to refuse it and no error to see. Append, never renumber; retire one by leaving the hole (the gaps between groups are for growth). TWO TRAPS, both paid for: (1) the drain MUST live in loop_step and NOT de_frame - de_frame is the HOST's entry and the native loop calls loop_step directly, so a drain in de_frame works perfectly under a DAW and does NOTHING under play.js, which is to say nothing any gate in this repo can see; it cost one confused round with the trace showing a knob that would not move while the queue filled up behind it. (2) BIND IN init(), NOT draw(), and before the rolling AUTOSAVE RESTORE - the knobs are drawn only on the FOCUSED face so binding where they are drawn makes parameters appear and vanish from the host menu as you tap around, and param_bind captures the slot as the DEFAULT, so binding after the restore tells the host that last session's values are the factory ones and its 'reset parameter' returns you to Tuesday. That framing also explains WHY the 303's default is transpose rather than it being an arbitrary pick, which the first framing ('is the PATTERN the instrument, or the VOICE?') never did - and it has a name in the world already: the drums half is the MPC's 16 LEVELS, the 303 half is Elektron's KEYBOARD mode. Two of the most-copied groove machines landed on the same gesture independently, so this ADOPTS a control rather than inventing one. PER MACHINE, not rack-wide, for a practical reason: the two kinds want OPPOSITE defaults (you almost always want the drum rack available and the 303 transposing), so one shared bit would force one of them wrong on every face change. The MOMENTARY half is the point - hold PTCH, throw a tuned kick fill or a two-bar acid lick over the running pattern, let go, back to the rack. (3) DROPPING the lens while a key is down STRANDS the note (the sequencer takes the line back and never sends a note-off for a key it did not press), and a momentary HOLD makes that the COMMON case rather than an edge one - let go of the button and the key together and one loses the race - so the lens hands the voice back explicitly. Per-BONE would buy a pot belly over a normal chest, or one arm longer than the other, and the machinery already takes it: bg[] and the derived segments are per bone, only the authoring is grouped. What that needs is a way to state it without a wall of numbers, which is a design question rather than a code one.
Poses are authored in degrees per joint, which is honest but blunt: what a build actually wants to say is 'stand like this', and the same attitude on a 0.72x kid and a 1.08x bruiser does not read the same. A named pose vocabulary (slouch, swagger, at-ease) resolved against the build would be the next step, and it is the same question the per-bone proportion rung asks: how do you state this without a wall of numbers.
The turnover's hip ARC is the one stated number in the whole flip. A placed figure has no ballistics to integrate, so the push off the floor is 12 authored px of lift shaped by a sine, not a trajectory anybody solved; take it out and the turnover reads as a body rotating about a nail driven through its pelvis. The honest version is the same centre-of-mass controller the fidget rung wants, and it would buy the thing this cannot do: a flip that MISSES.
A cartwheel in place is a turnover, not a cartwheel. A real one travels, hand-hand-foot-foot, and lands a body-width sideways; this one comes back down where it left. Travel is not another rest pose, it is a contact policy (which hand is down, when it is allowed to leave, what carries the weight in between), which is the same locomotion question the fidget rung asks and the reason both are parked behind the same controller.
Mid-turnover a figure is PLACED, so it can sweep through a neighbour: the stagger stops any two being horizontal at the same moment, but adjacent phases still overlap in space, and a placed body shoves a simulated one. Measured at up to 7 px of drift during the wave, against the 25 px the held handstand slides on its own, so it is currently the smaller of the two effects. The real fix is a contact policy for a body that is being placed rather than wider spacing.
The idle fidget is three hand-authored sinusoids per build, which is enough to stop them reading as props but is not a MOTION model: nothing in it knows where the figure's weight actually is, so it cannot catch a stumble or lean into a shove. The honest version reads the centre of mass and steers the ask from it, which is the same controller a walk cycle would need and is where this cart would turn into a locomotion probe.

THINK-ABOUT (not a bug — current behaviour is correct): TIE and a same-pitch SLIDE are the SAME sound in the common case — verified byte-identical WAV renders (same pitch, no accent: re-asserting the same note_vol + a glide to the same pitch is a true no-op, even across a 1s hold). They only diverge (a) at DIFFERENT pitches — then slide is a real portamento, not a hold — or (b) with ACCENT on the held step, where slide re-runs note_vol → a ~2.8dB mid-note swell a tie can't make (and the UI force-clears a tie step's own note, so a tie can't carry accent anyway). So is the TIE row redundant? No — it earns its place on ERGONOMICS, especially LIVE: with a tie you lengthen a note as a single event, so while the loop plays you can grab that one note and re-pitch it on the fly — the hold follows. The slide-fake is two pitch-matched steps, so re-pitching live means editing both in lockstep or it decays into a glide; you can't tweak a long note quickly mid-performance. (Also pitch-agnostic + edit-stable in the static case.) Leaning keep; parked here in case the flag rows ever get simplified.
